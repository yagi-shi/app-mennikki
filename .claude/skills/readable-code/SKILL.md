# リーダブルコード

書籍『リーダブルコード — より良いコードを書くためのシンプルで実践的なテクニック』（ダスティン・ボズウェル、トレバー・フーシェ 著、角征典 訳、オライリー・ジャパン、2012 年。原題 The Art of Readable Code）の内容を、章の順にまとめたもの。本の文章を写したものではなく、要点を短くまとめている。

- このスキルには、本の内容だけを書く。本にない決まりは足さない
- 本の例は C++、Python、JavaScript、Java で書かれている。ここでは、Swift に読み替えた短い例だけを載せる。例の中の型や関数は、説明のための仮のもの
- プロジェクト固有の決まりは、CLAUDE.md に書く

---

## 第 1 部 表面上の改善

### 第 1 章 理解しやすいコード

- **読みやすさの基本定理:** コードは、他の人が最短時間で理解できるように書く
- ここでの「理解する」とは、コードを変更したり、バグを見つけたりできるまで分かること
- 「他の人」には、数か月後の自分も含まれる
- コードは短いほうがよい。ただし、短くすることより、理解するまでの時間を短くすることのほうが大切

### 第 2 章 名前に情報を詰め込む

- **明確な単語を選ぶ:** `get` のような意味の広い単語より、何をするかが分かる単語を選ぶ（例: 取ってくるなら `fetch`、ダウンロードするなら `download`）
- **汎用的な名前を避ける:** `tmp`、`retval`、`foo` のような名前は、中身を表していない。値の目的や中身を表す名前にする
  - `tmp` は、短い間だけ値を置いておくことが、その変数の唯一の目的のときに限って使ってよい
  - ループの `i`、`j`、`k` は、入れ子になって取り違えやすいときは、何の番号かが分かる名前にする
- **抽象的な名前より具体的な名前を使う**
- **名前に情報を追加する:**
  - 値に単位があるなら、単位を名前に入れる（例: `delaySeconds`、`sizeMB`）
  - 注意が必要な状態や性質は、名前に入れる（例: 暗号化されていないパスワードなら `plaintextPassword`）
- **名前の長さを決める:**
  - スコープが小さければ、短い名前でよい。スコープが大きいほど、多くの情報を名前に入れる
  - 長い名前でも、入力補完があるので入力の手間は問題にならない
  - 省略形は、新しく加わった人が意味を理解できるものだけにする
  - 情報を損なわない、不要な単語は取り除く（例: `convertToString` → `toString`）
- **名前のフォーマットで情報を伝える:** 大文字・小文字や区切り方を使い分けて、名前の種類（型、定数、変数など）が分かるようにする

```swift
// 例: 単位と、注意が必要な情報を名前に入れる
let delaySeconds = 0.5
let plaintextPassword = passwordField.text
```

### 第 3 章 誤解されない名前

- 名前を付けたら、「他の意味と間違えられることはないか」と自問する
- **意味があいまいな単語を避ける:** 例えば `filter` は、条件に合うものを「残す」のか「除く」のか分からない。残すなら `select`、除くなら `exclude` のように、はっきりした単語にする
- **限界値には `max`・`min` を使う**（例: 上限なら `maxItems`）
- **範囲の指定:**
  - 終わりを含む範囲は `first`・`last`
  - 終わりを含まない範囲は `begin`・`end`
- **ブール値の名前:**
  - `is`・`has`・`can`・`should` などを使い、true か false かの意味が分かるようにする
  - 否定形の名前を避ける（例: `disableSSL` より `useSSL`）
- **ユーザーの期待に合わせる:** 多くの人は、`get` で始まる関数や `size` は軽い処理だと考える。時間のかかる処理に、そう受け取られる名前を付けない
- 名前の候補を複数考え、それぞれが誤解されないかを比べて選ぶ

```swift
// 例: 否定形を避ける
// 直す前
if !isNotFavorite { ... }
// 直したあと
if isFavorite { ... }
```

### 第 4 章 美しさ

- 読み手が慣れているパターンと一貫性のある、整ったレイアウトにする
- **似ているコードは、似ているように見せる**
- **関連するコードをまとめて、ブロックにする**
- 一貫性のある、簡潔な改行位置にする
- 必要なら、メソッドを使って整列させる。列をそろえると、違いや誤りが見つけやすくなる
- **一貫性のある、意味のある並び:** 宣言などを並べるときは、意味のある順番にし、どこでも同じ順番にする（例: 画面のフィールドの順番、重要な順、アルファベット順）
- **コードを「段落」に分割する:** 空行で区切り、論理的なまとまりを見えるようにする
- 一貫性のあるスタイルは、「正しい」スタイルよりも大切。プロジェクトの既存のスタイルに合わせる

### 第 5 章 コメントすべきことを知る

- コメントの目的は、書き手の意図を読み手に知らせること
- **コメントするべきではないこと:**
  - コードからすぐに分かること
  - ひどい名前を補うためのコメント。コメントで補わず、名前を変える（優れたコードは、ひどいコードに優れたコメントを付けたものより良い）
- **自分の考えを記録する:**
  - なぜそうしたのか、ほかの方法を選ばなかった理由など、コードを書いたときの大切な考え
  - コードの欠陥。決まった印を付けて書く（`TODO:` あとで手を付ける、`FIXME:` 動かないことが分かっている、`HACK:` あまりきれいではない解決策、`XXX:` 危険で大きな問題がある）
  - 定数の値に込めた意味（なぜその値なのか、どの程度まで変えてよいのか）
- **読み手の立場になって考える:**
  - 読み手が質問しそうなことを想像して、答えを書いておく
  - 読み手がはまりそうな罠を、先に知らせる
  - ファイルやクラスについての、全体像のコメントを書く
  - 関数の中の処理のまとまりに、何をしているかの要約コメントを書く
- コメントを書くのに迷ったら、まず頭に浮かんだことをそのまま書き、それから表現を改善する

```swift
// 例: 定数の値の意味を書く
// 大きくしすぎると、一覧の表示が遅くなる
static let maxVisibleRecords = 100
```

### 第 6 章 コメントは正確で簡潔に

- コメントは簡潔にする。少ない文字で多くの情報を伝える
- **あいまいな代名詞を避ける:**「それ」「これ」が何を指すかを、名詞で書く
- 歯切れの悪い文章は、正確な言葉に直す
- **関数の動作を正確に書く**
- **入出力の実例を使う:** 端のケースの入力と出力を、具体例で示す
- **コードの意図を書く:** コードが何をしているかを繰り返すのではなく、より高いレベルで、何をしようとしているかを書く
- 情報密度の高い言葉を使う。広く知られた用語（キャッシュ、正規化 など）で言えることは、その用語で書く
- 関数を呼ぶ側で引数の意味が分からないときは、名前で分かるようにする（Swift では、引数ラベルで表す）

## 第 2 部 ループとロジックの単純化

### 第 7 章 制御フローを読みやすくする

- **条件式の引数の並び順:**
  - 左側には、調査の対象になっている、変化する値を書く
  - 右側には、比較の対象になる、あまり変化しない値を書く（例: `if length >= 10`。`if 10 <= length` にしない）
- **if / else ブロックの並び順:**
  - 否定形より、肯定形の条件を先に書く
  - 単純な条件を先に書く
  - 関心を引く条件や、目立つ条件を先に書く
  - これらがぶつかるときは、判断して選ぶ
- **三項演算子:** 行数を短くするより、他の人が理解するまでの時間を短くすることを優先する。基本は if / else を使い、簡潔になるときだけ三項演算子を使う
- **do / while ループを避ける:** 条件が後ろにあると、読み手は本体を二度読むことになる（Swift では `repeat-while`）
- **関数から早く返す:** 前提に合わない場合は、早めに返す（Swift では `guard`）
- **ネストを浅くする:**
  - 早めに返して、ネストを減らす
  - ループの中では、`continue` を使ってネストを減らす
- **実行の流れを追えるようにする:** スレッド、割り込み（シグナル）、例外、関数ポインタと無名関数（Swift ではクロージャ）、仮想メソッド（Swift ではオーバーライド）は便利だが、処理の流れを分かりにくくする。これらを使ったコードの割合が高くなりすぎないようにする

```swift
// 例: 早めに返して、ネストを浅くする
// 直す前
func save() {
    if !storeName.isEmpty {
        if let rating = selectedRating {
            repository.create(storeName: storeName, rating: rating)
        }
    }
}

// 直したあと
func save() {
    guard !storeName.isEmpty else { return }
    guard let rating = selectedRating else { return }

    repository.create(storeName: storeName, rating: rating)
}
```

### 第 8 章 巨大な式を分割する

- **説明変数:** 式の意味を説明する名前の変数に、式を入れる
- **要約変数:** 大きなコードの塊を、小さな名前に置き換えて、扱いやすくする
- **ド・モルガンの法則を使う:** 否定をまとめて、条件式を読みやすくする（`!(a && b)` は `!a || !b`、`!(a || b)` は `!a && !b`）
- **短絡評価を悪用しない:** 処理を 1 行に詰め込むために、`&&` や `||` の短絡評価を使わない
- **複雑なロジックは、反対から考える:** 条件が複雑になったら、逆の条件（例:「重なる」の代わりに「重ならない」）で考えると単純になることがある
- **巨大な文を分割する:** 同じ式の繰り返しは、変数や関数にまとめる

```swift
// 例: 説明変数と要約変数（動きは変えない）
// 直す前
if user.id == document.ownerID || user.isAdmin {
    // ...
}

// 直したあと
let isOwner = user.id == document.ownerID
let canEditDocument = isOwner || user.isAdmin
if canEditDocument {
    // ...
}
```

### 第 9 章 変数と読みやすさ

- 変数が多いほど、変数のスコープが広いほど、値が変わるほど、コードは追いにくくなる
- **変数を削除する:**
  - 役に立たない一時変数（式を分かりやすくもせず、1 回しか使わないもの）
  - 中間結果を入れておくだけの変数。すぐに結果を使えるなら、使う
  - 制御フロー変数（ループを抜けるためだけのフラグなど）。早めに返すなどで、なくせることが多い
- **変数のスコープを縮める:**
  - 変数が見えるコードの行数を、できるだけ少なくする
  - グローバル変数を避ける。プロパティにしなくてよい値は、関数の中の変数にする
  - 変数は、使う直前で定義する
- **変数は一度だけ書き込む:** 値を変えない変数は、変えられないようにする（Swift では `let`）

## 第 3 部 コードの再構成

### 第 10 章 無関係の下位問題を抽出する

- 関数やコードのまとまりを見て、「高レベルの目標は何か」と自問する
- 目標に直接関係のない、別の下位問題を解いているコードがあれば、別の関数に抽出する
- **純粋なユーティリティコード**（文字列の処理、日付の計算 など）は、抽出しやすい。汎用的なコードとして作ると、プロジェクトのほかの場所でも使える
- プロジェクトに特化した処理でも、下位問題なら抽出できる
- 使いにくい既存のインタフェースは、簡潔なインタフェースで包んで使う
- **やりすぎない:** 小さな関数を作りすぎると、かえって読みにくくなる

### 第 11 章 一度に 1 つのことを

- コードは、1 つずつタスクを行うようにする
- 手順:
  1. コードが行っているタスクを、すべて列挙する
  2. タスクごとに、別の関数か、少なくともコードの別の段落に分ける

### 第 12 章 コードに思いを込める

- 自分のしたいことを、簡単な言葉で説明できるようにする
- 手順:
  1. コードの動作を、簡単な言葉で同僚に説明するように書き出す
  2. その説明の中のキーワードや言い回しに注目する
  3. その説明に合わせて、コードを書く
- **ライブラリを知る:** 説明を短くするには、使えるライブラリが何をしてくれるかを知っておく
- 問題を声に出して人に説明すると、解き方が見えてくることがある（ラバーダッキング）

### 第 13 章 短いコードを書く

- **きっと必要ない機能は、実装しない:** 必要以上に機能を作ると、テスト、文書、保守の手間が増える
- **質問と要求の分割:** 要求が本当に必要か問い直し、分けて考えると、問題をもっと簡単にできることがある
- **コードを小さく保つ:**
  - 汎用的なユーティリティを作り、重複したコードを減らす
  - 使っていないコードや、役に立たない機能は削除する
  - プロジェクトを、独立した小さな部分に分ける
- **身近なライブラリに親しむ:** 標準ライブラリにどんな機能があるかを、ときどき見ておく。自分で書く前に、ライブラリで済まないかを考える

## 第 4 部 選抜テーマ

### 第 14 章 テストと読みやすさ

- テストのコードも、読みやすく、保守しやすくする。テストが読みにくいと、テストを直すのが怖くなり、テストを増やさなくなる
- **大切ではない詳細は隠し、大切な詳細は目立たせる:** 準備などの細かいコードは、ヘルパー関数にまとめる
- テストは、何を確かめているかが、最小限の文で分かるように書く
- **エラーメッセージを読みやすくする:** 失敗したときに、何がどう違ったかが分かるようにする（Swift Testing の `#expect` は、比べた値を表示する）
- **適切な入力値を選ぶ:** コードを完全にテストできる、最も単純な入力値を選ぶ
- **1 つの機能に、複数のテスト:** 1 つの大きなテストより、確かめる観点ごとの小さなテストに分ける
- **テスト関数に名前を付ける:** 何を、どんな状況で確かめるかが分かる名前にする
- **テストしやすいコードは、設計が良い:** テストしにくいと感じたら、設計を見直す（グローバル変数や外部への依存が多いなど）
- **やりすぎない:** テストのために、本番のコードの読みやすさを損なわない。網羅率 100% にこだわらない

```swift
// 例: テストの名前と、最小限の入力値
@Test("店名で検索すると、店名にその文字を含む記録だけが残る")
func searchByStoreNameKeepsMatchingRecords() {
    let viewModel = makeViewModel(storeNames: ["中華そば 山田", "らーめん 田中"])

    viewModel.searchText = "田中"

    #expect(viewModel.items.map(\.storeName) == ["らーめん 田中"])
}
```

## 見直しの観点（本の章ごとの要点）

コードを書いたあとや変更したあとに、本の章ごとに確かめる。

- [ ] 第 1 章: 他の人が、最短時間で理解できるか
- [ ] 第 2 章: 名前に、中身、目的、単位、注意すべき情報が入っているか。汎用的な名前が残っていないか
- [ ] 第 3 章: 名前が、他の意味と誤解されないか。限界値、範囲、ブール値の名前の付け方に沿っているか
- [ ] 第 4 章: 似ているコードが似ているように見えるか。意味のある順番に並び、段落に分かれているか
- [ ] 第 5 章: コードから分かることをコメントしていないか。なぜそうしたか、罠、全体像が書かれているか
- [ ] 第 6 章: コメントが正確で簡潔か。あいまいな代名詞がないか
- [ ] 第 7 章: 条件式の並び、if / else の順番、ネストの深さが読みやすいか
- [ ] 第 8 章: 巨大な式を、説明変数や要約変数に分けられないか
- [ ] 第 9 章: 不要な変数がないか。スコープが広すぎないか。変えない値が `let` になっているか
- [ ] 第 10 章: 目標と関係のない下位問題を、抽出できないか
- [ ] 第 11 章: 一度に複数のタスクを行っていないか
- [ ] 第 12 章: 処理を簡単な言葉で説明でき、その説明どおりの形になっているか
- [ ] 第 13 章: 必要のない機能を作っていないか。ライブラリで済むものを自分で書いていないか
- [ ] 第 14 章: テストが読みやすく、名前と入力値から何を確かめているかが分かるか
